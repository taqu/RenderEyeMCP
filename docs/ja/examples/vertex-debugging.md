# シナリオ D4 — 頂点シェーダーデバッグ

## 問題

変換後にメッシュの頂点が間違った位置に現れています。特定の頂点の頂点シェーダーを
ステップ実行して MVP 行列乗算の結果を確認し、変換がどこで間違っているかを
突き止めます。

## 準備

1. RenderEyeMCP 拡張機能を有効にした状態で RenderDoc が起動していること。
2. キャプチャがロードされていること。
3. 位置がずれたメッシュのドローコールが選択済みまたは把握されていること。

## プロンプト例

**クイック調査:**
> ドローイベント 310 の頂点 0 が間違ったクリップ空間位置になっています。
> 頂点シェーダーをステップ実行して変換がどこで壊れているか見つけてください。

**詳細な調査:**
> ドローイベント 310 のメッシュが画面の間違った位置に表示されています。まず頂点 0 の
> オブジェクト空間位置とPost-VS位置を確認して問題の規模を把握してください。次に頂点 0 の
> 頂点シェーダーをデバッグしてください。ワールド空間位置が初めて極端または誤った値になる
> ステップを見つけてください。そのステップでモデル行列とワールド空間位置変数を検査し、
> 誤った行列コンポーネントを特定してください。

## 調査内容

- 影響を受ける頂点のオブジェクト空間位置(変換前)
- Post-VS位置で頂点が画面外にあること、どれくらい外れているかを確認する
- 頂点 0(または別の代表的な頂点)の頂点シェーダーデバッグトレース
- ワールド空間位置が初めて誤った値になる実行ステップ
- そのステップでのモデル行列の値。特に予期しないスケールまたは平行移動コンポーネント

## 期待される結果

完全な調査では問題の原因となる特定の行列コンポーネントを特定できます。例: Post-VS NDC y = 200
([-1,1]を大幅に超える)、頂点シェーダーステップ8でモデル→ワールド変換後に`pos_ws.y = 1000.0`
が示され、`model_matrix[1][1] = 1000.0`でYスケールが1ではなく1000であることが確認される。

| ステップ | 観察 |
|---|---|
| Post-VS クリップ: NDC y = 200 | 頂点が Y 方向に 200 倍ずれている |
| 頂点シェーダーステップ 8: `pos_ws.y = 1000` | モデル→ワールド変換が Y を 1000 倍している |
| `model_matrix[1][1] = 1000.0` | 確認: モデル行列アップロードの Y スケールが間違っている |

## 結果の解釈

モデル→ワールド変換は通常、頂点シェーダーで最初に適用される行列です。ステップ8の後に
ワールド空間位置がすでに間違っている場合、モデル行列自体が間違っています。アプリケーション内で
それが計算またはアップロードされる箇所を確認してください。

ワールド空間位置が正しいがクリップ空間位置が間違っている場合、ビュープロジェクション行列が
原因です。初期化時に一度だけ設定されてカメラに追従して更新されていない行列を探してください。

## 制限事項

- 頂点シェーダーデバッグは単一頂点呼び出しのみをデバッグします。他の頂点は異なる
  値を持つ場合があります; 必要に応じて追加の頂点に対して繰り返してください。
- インデックス付きドローの場合はインデックスバッファの値を `idx` として渡します。
  非インデックスドローの場合は `idx = vert_id + base_vertex` です。
- API またはドライバーが頂点シェーダーデバッグをサポートしない場合は
  `error: debug_vertex_unsupported` を返します。
